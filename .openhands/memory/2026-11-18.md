the free-gas XS but NOT for the thermal law (raises "does not bound 873 K"). So the
slope is a 600-800 K chord, and the Java scaling factor is *anchored* at the core's
nominal graphite temperature (600 degC = 873.15 K) so the correction is a perturbation
about nominal (factor = 1 there -> seed-critical preserved). Honest caveat recorded in
the resource note: the ss21/ss12 slopes are nonlinear, so this overestimates at 873 K.

**THE MATCHED-PAIR FINDING (important).** The slopes are *fractional* changes of the
OpenMC cell's constants, so they are valid ONLY against the OpenMC-derived lattice
table. Against the shipped 1-D table (whose sr1/ss21 differ ~9-360x) the whole-core
effect flips NEGATIVE (-2.4e-5/degC). Fix: `RbmkGraphiteTemp.matchesLattice()` gates
the link on `LatticeTable.source().startsWith("openmc")`. It is a no-op with the 1-D
table. **Consequence: the graphite link and the pending OpenMC-table shipment (Step 1b)

   restoring power to ~0.98. Xe-135 is burned off by flux faster than produced at

   30 min = 1/4 of one I-135 half-life. The pit is a LOW-flux, HOURS-long effect.
   Fix: hold 200 MWt (what the operators held 00:28–01:23) and let АР withdraw rods.
   Now Xe→1.76x and insertion 0.900→0.782, which IS the historical operating decision.
2. **`setAutoRegulator` latched its setpoint to the CURRENT power.** Called before
   recovery, that is ~0, so "holding power" parked the core dead and every later

## THE BIG FINDING — the bare `RbmkTransientSolver` has NO thermal feedback

Settle-duration sweep (how long the 400×0.05 s settle loop runs) on the ORIGINAL
frozen-temperature test:

|---|---|---|---|
| 5 s  | 1.044 |  1.533 | +214.4 % |

| 20 s | 1.163 |  5.630 | +188.0 % |
| 40 s | 1.316 | 32.818 | +162.3 % |

**"Starting power" was just how long the settle loop ran** — an exponential sampled
at an arbitrary time. Any peak figure quoted from that path is arbitrary.

Cause: the solver takes fuel temperature as an INPUT; nothing relaxes it. The
production path (`UnifiedReactorCore`) does relax it (TAU_FUEL=10 s, TAU_GRAPHITE=30 s,
anchored to `FuelTemperature.MAX_FUEL_C`=600 °C). The variants test bypassed that.

### Wiring the derived fuel temperature changes the headline number a LOT
Frozen vs relaxing fuel temperature (same solver, same scram rate):
- normal run: peak +0.4 % both ways (insensitive)
- **26 April: peak +188.0 % frozen vs +140.2 % relaxing** (my crude power-tracked
  proxy); with the anchored `FuelTemperature` form, **+89 %**, and P0 settles to 3.28.
A 48–99 point swing in the project's headline number. Doppler is not a detail here.

### But the accident state STILL does not settle — and that is a TEST-DESIGN bug
Even with feedback wired, state B (void 0.10, rods 0.08, **xenon 1.0**) never
converges: 20 s→3.28, 40 s→9.98, 80 s→31.6. It is not a critical operating point at
all — it is seeded BARE and supercritical, so it is still an exponential.

**Root-find: state B needs Xe ≈ 3.12 to be critical** (bisection on
`solver.balanceKeff()`, keff 1.000016 at Xe=3.1211). With Xe=3.12 the run DOES
settle (P0 0.96→1.20 over 20–160 s instead of 3.3→31.6) — still drifting slowly, so
the settle is not fully converged either.

The physically correct accident state is critical *because of* xenon poisoning —
that is the whole point of the ORM violation and the 26 April state. Seeding it with
xenon 1.0 (a clean, unpoisoned core) is unphysical.

**DECISION NEEDED (Ben):** how to define the two starting states. Options:
(a) solve the xenon that makes each variant exactly critical at its rod position
    (self-consistent, but a long bisection per run);
(b) start both from `UnifiedReactorCore`'s `selfConsistentSeed()` and drive them
    there with the regulator (slow, but no invented numbers);
(c) run the variants ON `UnifiedReactorCore` (like `AccidentSequence` does) instead
    of the bare solver, and drop this test's bespoke seeding entirely.
I lean (c): it removes a whole duplicated feedback path and the test then measures
the reactor the game actually runs. Not done — it changes what the test asserts.
